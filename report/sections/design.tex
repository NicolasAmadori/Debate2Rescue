\section{Design}
\label{sec:design}

\subsection{Architecture}
\label{subsec:architecture}

The system consists of a multi-agent architecture designed to separate the physical simulation environment, the BDI reasoning loop, and the argumentation engine.

Agent-environment interaction follows the standard perception-action loop: agents receive environmental percepts and perform physical actions.
Agent coordination is realized through asynchronous messages using both standard and custom performatives designed for argumentation dialogues.

The architecture consists of five main layers:
\begin{enumerate}
    \item \textbf{Environment and Simulation Layer (Java):} Composed of the simulation environment (\texttt{EmergencyEnvironment}) and the domain model (\texttt{SimModel}), this layer manages the 2D grid, obstacles, stations, and emergencies. A dedicated thread generates emergencies according to the selected spawn rates, while the environment executes agent actions and updates agent percepts.
    
    \item \textbf{MAS Infrastructure Layer (Jason):} This layer is based on the centralized Jason infrastructure declared in \texttt{debate2rescue.mas2j} and manages the execution cycle of BDI agents, scheduling plan intentions and delivering messages through the agent communication channel.
    
    \item \textbf{Agent Layer (AgentSpeak):} Defines the autonomous entities that operate in the system: the Orchestrator, Rescuers, and Pilots. Agents maintain local beliefs, react to environment percepts, and coordinate through communication protocols.
    
    \item \textbf{Argumentation Layer (Arg2P):} Implements argumentation-based debates using Arg2P. It evaluates argumentation theories defined in Prolog and, through the use of custom Jason internal actions, integrates the results with the BDI agents.
    
    \item \textbf{Observability and User Interface Layer (Swing):} It provides a real-time visual representation of the grid, dynamic controls for simulation parameters, an interactive debate arena, and an audit logger that persists debate transcripts to disk.
\end{enumerate}

\Cref{fig:architecture_diagram} illustrates the overall system architecture and the relationships among the five layers, highlighting the communication channels and data flow between the Java simulation environment, the Jason BDI runtime and agents, the Arg2P argumentation engine, and the Swing graphical user interface.

\subsection{Detailed Design}
\label{subsec:detailed_design}

\subsubsection{Operational Workflows}

The overall response cycle proceeds through four sequential phases:

\begin{enumerate}
    \item \textbf{Emergency Detection and Dispatch:} When an emergency appears on the grid, the orchestrator receives the corresponding percept. It identifies all idle rescuers, calculates their grid distance to the incident, and assigns the closest one. The assigned rescuer navigates step by step toward the incident location.
    
    \item \textbf{On-Site Triage:} Upon reaching the emergency cell, the rescuer invokes \texttt{start\_rescue} to uncover the specific attributes of the incident: severity level, victim count, trapped individuals, escalating danger, physical size, and collateral risk. Using a local belief table, the rescuer identifies the required resource and sends a request to the orchestrator.
    
    \item \textbf{Request Window and Contention Detection:} To avoid greedy, first-come-first-served allocations, the orchestrator groups incoming requests within a short time window. Once the window closes:
    \begin{itemize}
        \item If the number of competing requests for a given resource type is less than or equal to the number of free units, the orchestrator grants the resources directly.
        \item If requests exceed the available units, resource contention occurs and the orchestrator starts a new debate.
    \end{itemize}
    
    \item \textbf{Rescue Execution:} The pilot assigned to the winning emergency travels to the site. The time required to resolve the emergency is proportional to the incident difficulty. Once resolved, the emergency is cleared from the environment, and both the rescuer and the pilot return to their base station, informing the orchestrator that they are free. Rescuers whose claims were denied remain on-site and increment their denial counter, gaining priority in subsequent allocation rounds.
\end{enumerate}

\subsubsection{Argumentation Model} %TODO: check if can refine or improve

Resource allocation disputes are solved through structured argumentation rather than numerical scoring functions.

The argumentation theory models claims, evidence, principles, and preference rules:
\begin{itemize}
    \item \textbf{Claims:} Contenders assert a claim for the resource (\texttt{claim(E)}). Initial claims temporarly grant the resource based merely on the emergency id $E$, oldest first.
    \item \textbf{Compare:} When two contenders have presented their values for the same reason $R$, they are automatically compared and who wins get an advantage. Advantages are ranked based on the strength of their reason $R$:
    \begin{center}
    \texttt{critical} $>$ \texttt{waiting} $>$ \texttt{catastrophic} $>$ \texttt{major\_disaster} $>$ \texttt{spreading} $>$ \texttt{severity} $>$ \texttt{collateral\_risk} $>$ \texttt{trapped} $>$ \texttt{escalating} $>$ \texttt{size} $>$ \texttt{victims}
    \end{center}
    Accumulated waiting time (the number of prior denials) outranks everything except a critical situation, to prevent starvation.
    
    \item \textbf{Situations:} Some values, alone or combined, define a dangerous situation, which is a reason placed in the same hierarchy (formalized in \cref{tab:impl_situations}). A single generic rule puts an emergency that is in a situation ahead of a contender that is not:
    \begin{itemize}
        \item \texttt{critical}: The incident has severity ESI 1 or 2.
        \item \texttt{catastrophic}: The incident presents collateral risk at medium or large scale.
        \item \texttt{major\_disaster}: The incident is large and has many victims.
        \item \texttt{spreading}: People are trapped and the incident is escalating.
    \end{itemize}
    
    \item \textbf{Tie-Breaking:} If two claims have identical attributes, the older emergency ID wins.
\end{itemize}

\subsubsection{Custom Performatives}
Standard agent communication languages provide general-purpose performatives, but lack speech acts dedicated to argumentation. We extend agent communication in Jason by introducing four custom performatives handled via the \texttt{+!kqml\_received} pattern:

\begin{itemize}
    \item \texttt{argue}: Sent by the orchestrator to all contending rescuers to formally initiate a debate and broadcast the contenders' initial claims (\texttt{move(RT, M, E, claim)}) for the contested resource type.
    \item \texttt{challenge}: Sent by a rescuer on its turn to the orchestrator (and relayed to all contenders) to attack a target competitor's claim by revealing an emergency attribute and its value (\texttt{challenge(RT, Target, Reason, Value)}) where the attacker holds an advantage.
    \item \texttt{answer}: Sent by a challenged rescuer to the orchestrator (and relayed to all contenders) to defend its claim against a specific challenge move ID (\texttt{answer(RT, M, Reason, Value)}), either by revealing a superior value on the disputed reason or by disclosing attributes that complete a situation.
    \item \texttt{concede}: Sent by a rescuer to the orchestrator (\texttt{concede(RT)}) when Arg2P finds no admissible move that improves its position. The orchestrator removes the rescuer from the active turn rotation, notifies remaining contenders to retract the conceded claim, and marks the request as denied for the current allocation round.
\end{itemize}

The end-to-end turn-based debate protocol between the Orchestrator and contending Rescuers is illustrated in \Cref{fig:debate_sequence}.
When resource contention occurs at the closure of a request window, the Orchestrator opens a debate and broadcasts the initial claims via \texttt{argue}. In subsequent turns, agents evaluate their local knowledge through Arg2P, issuing attacks (\texttt{challenge}) or defenses (\texttt{answer}), which the Orchestrator records and relays to maintain synchronized debate models across all contenders. Once a contender cannot construct an improving move, it emits \texttt{concede}, allowing the Orchestrator to conclude deliberation and dispatch the disputed resource to the winner.

\subsubsection{Internal Actions}

Two custom Jason internal actions integrate Arg2P into the agents' reasoning cycles:

\begin{itemize}
    \item \texttt{arg.deliberate(Moves, Labels)}: Executed by the orchestrator. It builds the argumentation theory from the move history, evaluates the graph using grounded semantics, and returns the status of each claim (\texttt{in}, \texttt{out}, \texttt{und}) along with the active winning justification (\texttt{winning\_reason}).
    
    \item \texttt{arg.choose(Moves, Me, Other, Candidates, Chosen)}: Executed by rescuers on their turn. It selects the first candidate that strictly improves its position against the target competitor, searching first one move ahead and then the combinations of two moves. If no candidate improves its position, the internal action fails, prompting the rescuer to send a \texttt{concede} move.
\end{itemize}

\subsection{Agent Modeling}
\label{subsec:agent_modeling}

\subsubsection{Orchestrator Agent}
\begin{itemize}
    \item \textbf{Beliefs:} Tracks detected emergencies (\texttt{emergency}), idle rescuers (\texttt{availableRescuer}), available resource units (\texttt{availableResource}), active collection windows (\texttt{window}), and debate states (\texttt{debate}, \texttt{debate\_id}, \texttt{move}, \texttt{turn}).
    \item \textbf{Plans:}
    \begin{itemize}
        \item \texttt{!assign}: Assigns available rescuers to new incidents, prioritizing the closest rescuer.
        \item \texttt{!close\_window}: Closes the request collection window and initiates resource allocation or debate.
        \item \texttt{!deliberate}: Evaluates whether a debate is needed or if resources can be granted directly.
        \item \texttt{!next\_turn} and \texttt{!give\_turn}: Coordinate turn rotation among contenders whose claims are not accepted under grounded semantics.
        \item \texttt{!grant}: Dispatches the nearest available pilot to the winning incident.
    \end{itemize}
    \item \textbf{Concurrency:} Critical plans handling resource state and debate updates are declared as atomic to ensure thread safety when concurrent events occur simultaneously.
\end{itemize}

\subsubsection{Rescuer Agent}
\begin{itemize}
    \item \textbf{Beliefs:} Stores the assigned emergency ID and location, perceived emergency facts, the required resource type (\texttt{requesting}), the accumulated denial count (\texttt{denials}), and the debate moves history.
    \item \textbf{Plans:}
    \begin{itemize}
        \item \texttt{!handle}: Receives an incident assignment, navigates to the target cell, and performs triage.
        \item \texttt{!evaluate} and \texttt{!make\_request}: Identifies the necessary specialized resource and submits the request to the orchestrator.
        \item \texttt{!your\_turn}: Activated when the orchestrator prompts the rescuer to speak. It evaluates candidate defenses or attacks via \texttt{arg.choose} and emits an \texttt{answer}, \texttt{challenge}, or \texttt{concede} message.
        \item \texttt{!go\_home}: Returns to the base station after emergency resolution and announces availability.
    \end{itemize}
    \item \textbf{Strategy:} Rescuers disclose emergency attributes incrementally only when required to counter an opponent's argument, minimizing communication overhead.
\end{itemize}

\subsubsection{Pilot Agent}
\begin{itemize}
    \item \textbf{Beliefs:} Maintains the assigned base station coordinates, its specialized resource type, and its availability status.
    \item \textbf{Plans:}
    \begin{itemize}
        \item \texttt{!start}: Initializes the agent in the environment and informs the orchestrator of its readiness.
        \item \texttt{!move\_to\_emergency}: Dispatched by the orchestrator upon winning a debate. The pilot navigates to the incident, simulates the rescue operation duration ($2 \times \mathrm{severity} + \mathrm{victims}$), resolves the emergency, signals the waiting rescuer, and returns to base.
    \end{itemize}
\end{itemize}
